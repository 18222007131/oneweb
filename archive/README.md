## 二、回归使用方式

平台开发完成后，以本目录为唯一基准执行回归：

1. 以 `03_regression_cases.json` 建立测试用例或测试管理条目；
2. 每一条用例必须对应 `02_rules_and_boundaries.md` 中的规则编号；
3. 对涉及日志/告警的用例，按 `04_test_evidence.md` 和 `logs/` 中保留的关键字段校验输出；
4. 对涉及 COP、热物性、PLC 的用例，使用固定测试时钟、固定 PLC 样本和固定种子数据，避免结果不可复现；
5. 平台实现不得为了“通过用例”修改业务规则；规则变更必须先更新本归档并提升版本号；
6. 回归必须同时验证**正向通过**和**边界拒绝**，尤其是库房前置核验、无合格库房、入库超时、到货偏差、审核整改和COP异常。

## 三、本基线中最容易被误改的规则

- **到货偏差只由吨位偏差 > 5% 触发**；温度只查询、记录、回溯，不触发重规划。
- 到货货温不得再与 q_resp 条件温度计算偏差后触发分支；q_resp 条件温度仍必须查询并写入历史。
- q_resp 条件温度与 PLC 参数必须一起进入 `thermalPlcHistory`，供回溯和复盘。
- 库房预选与 reviewer 前置核验发生在**用户选择之前**；不合格库房不得展示给用户。
- 前置核验不通过只回退 scheduler 重选，不进入普通单据整改重试。
- 所有果品（杨梅/柚子/苹果）的内置温湿度参数必须完整；reviewer payload 必须携带 `builtInFruitSpecs`。
- 无合格库房时直接终止，不进入 reviewer，不写台账。
- 入库超时预约禁止直接入库；重预约走完整预约→筛选→前置核验→选择流程。
- COP 单库房与机组分摊必须分开计算、分开存储、分开做历史比对。
- COP 异常警报不阻塞到货/新预约；设备异常才阻止同机组库房新预约，且必须手动解除。

## 四、日志说明

`logs/` 中保存的是本次调试会话中实际产生的**关键日志片段**，用于证明关键分支和字段已经出现；完整逐行控制台输出没有全部持久化，未在此伪造。

平台回归时应以“用例 + 规则 + 日志关键字段”三者共同判定，而不是只匹配某一句自然语言。

- 源码快照只用于对照 Demo 行为，不作为平台正式代码。
